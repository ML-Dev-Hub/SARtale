Contributing

Small, tested changes with a clear reason are the easiest to review. Every number on the site must trace back to the data or a cited source.

Before you open a pull request#

npm --prefix app test -- --run
npm --prefix app run build
cd processing && conda run -n sartale pytest tests -q

All three must pass. Add a test for each change in behaviour, next to the code it covers: app/src/*.test.ts or processing/tests/test_*.py.

Ground rules#

  • Numbers come from the data. Use a token from lakes.json in page text rather than typing a figure. If a number is not in the data, cite its source next to it.
  • Screening, not warning. Do not describe a status as a hazard, a prediction or a warning. The wording check in content.ts enforces the main phrases.
  • Constants live in one place. Method constants belong in processing/sartale/config.py; the build copies them into lakes.json for the app.
  • Same track only. Never compare areas across tracks or viewing directions in the status.
  • No secrets in the repository. Earthdata logins stay in ~/.netrc locally and in the earthdata environment on GitHub; other keys in a git-ignored .env.local.
  • Data stay out of git. Downloaded windows live in data/, which is ignored.
  • Lake requests are issues. Accept or reject them on GitHub as described in Lake requests; do not edit requests.json by hand, because the workflow rewrites it.

Changing the method#

A change to the dark rule, the shadow rule, the zone or the status test changes every number on the site and in both videos. Run the whole pipeline, check that the Attabad gate still passes, compare the new lakes.json with the old one, and say in the pull request which lakes changed status and why.

AI tools#

AI tools helped write the code, the copy and the videos; none runs in the pipeline or the app. What each tool did is recorded in SI_USE.md. Update it when you use one for a contribution.
