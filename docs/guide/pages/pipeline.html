Pipeline

The pipeline in processing/ rebuilds the lake data from NASA's archive. The team runs it; the website only reads what it writes.

Before you start: create the sartale conda environment (Getting started) and save a NASA Earthdata login in ~/.netrc. Never commit the .netrc file or paste its contents anywhere.

Run it

All commands run from processing/, through one entry point, python -m sartale.run_pipeline:

cd processing
conda run -n sartale python -m sartale.run_pipeline lakes-search   # 1. find NISAR passes over each lake
conda run -n sartale python -m sartale.run_pipeline lakes-fetch    # 2. cache a 6 km window per pass (restartable)
conda run -n sartale python -m sartale.run_pipeline lakes-absence  # 3. re-check the sites with no lake now
conda run -n sartale python -m sartale.run_pipeline lakes-build    # 4. write lakes.json and the lake pictures
conda run -n sartale python -m sartale.run_pipeline lakes-check    # 5. compare radar water with Sentinel-2 water

lakes-absenceRe-checks every site with no lake now with Sentinel-2, all year: the newest scene since the last check (or, for a site with none yet, in the last 400 days) whose lake zone is at least 80% clear of cloud, shadow, snow and ice, with snow or ice on no more than 1% of it. Water above the site's threshold makes it Lake may be forming. When no scene qualifies, or the search fails, the last check stands with the date of the search. The rebuild runs it before lakes-build, so the build carries the new check (and a forming site keeps its radar water layer) in the same refresh; --only-missing, after the build, checks a site new to the registerlakes.json, Earth Searchabsence_checked and the status in lakes.json; lakes-build carries the last check forward while the zone is the same
lakes-diffCompares a previous lakes.json (--old) with the new one pass by pass: prints added and dropped passes per lake, writes them to the GitHub job summary, warns for every dropped pass and every lake whose latest date moved back, and exits 1 if more than a quarter of the previous passes would be dropped. Each command takes --help. The paths above are the defaults, and each one can be overridden with a flag: --lakes-in, --passes, --cache, --out or --checks.

The Attabad gate

lakes-build refuses to call a build good unless the method can tell a real lake from no lake. Attabad is a large, permanent lake; at the Shisper point, the basin of an ice-dammed lake that drained in 2022, there is no lake now. On each shared track, Attabad's water area must be at least twice Shisper's (median ratio ≥ 2), Attabad must have a status, and it must have at least 3 looks in the cloud window. If the gate fails, lakes.json is still written for inspection, but the command exits 1. Pass --allow-gate-fail only while debugging, and never ship that build.

Add a lake by hand

  1. Add an entry to processing/lakes_in.json (fields in Data files). Every coordinate needs a published source in coord_source.
  2. If the lake has an outline, save it as GeoJSON in processing/outlines/ and set outline to its path relative to processing/.
  3. Run lakes-search, lakes-fetch and lakes-build, then pytest tests -q and npm --prefix app test -- --run.

A lake put forward on the website goes through the same steps after a team member accepts its GitHub issue and lake-issue-accept adds its entry. See Lake requests.

Troubleshooting

  • 401 or a login page from ASF: the Earthdata login in ~/.netrc is missing or wrong, or the ASF application has not been authorised in your Earthdata profile.
  • lakes-fetch exits 1: some passes failed, usually because of the network. Run it again; cached windows are kept.
  • The gate fails after a change to the method: read the per-track ratios it prints. A drop usually means the dark rule or the shadow rule now removes real water.
